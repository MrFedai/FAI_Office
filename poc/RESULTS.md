# Phase 1 — measured results

Raw numbers from the proofs of concept. Each entry: what ran, where, with which inputs, median of 3 runs.
Host numbers are a development PC (WSL2, x86-64), not the reference device; they show feasibility, not budgets.
Budget verdicts come only from the reference Android device.

## Seed corpus (WP3)

Generated by `corpus/gen.py` from flat ODF sources through headless LibreOffice 26.8.2. Freely redistributable
(generated content). Text is mixed English / Turkish, fonts Liberation Serif / Sans.

| File | Pages / size | Content |
|---|---|---|
| long-100p.pdf | 101 pages, 2.1 MB | headings, justified text, tables, PNG images, header, footer with page fields |
| typical-20p.docx / .odt / .pdf | 20 pages, ~1 MB | same structure, the "typical 20-page DOCX" of section 7 |
| typical.xlsx / .ods | 2 sheets, 2000 rows | numbers, row formulas, running total, SUMIF / AVERAGEIF summary |
| typical.pptx / .odp | 12 slides | titles, bullet lists, PNG images, custom shapes |

Not yet covered: RTL, CJK, embedded subset fonts from other producers, forms, annotations, encrypted PDF,
Microsoft-produced OOXML. These come with the fidelity test plan (deliverable 9).

## PoC-2 — PDFium WASM in a browser (WP2)

`pdfium-web/` · PDFium chromium/8111 prebuilt, wasm · headless Chromium (Playwright build 1248), desktop host
· render width 1080 px · `long-100p.pdf` · cache disabled, local server

| Metric | Result |
|---|---|
| pdfium.wasm size | 5.2 MB raw, 2.4 MB gzip -9 |
| pdfium.js size | 161 KB raw, 29 KB gzip -9 |
| WASM ready (fetch + compile + init, local) | ~70 ms |
| Document load | ~5 ms |
| First page rendered to canvas | ~43 ms (page script start to visible: ~130 ms) |
| Other pages, average / worst | 7.8 ms / 26 ms |
| WASM heap | 17.9 MB |

Findings:

* PDFium WASM alone is ~2.4 MB compressed, about half of the 5 MB Web initial-load budget for the whole light
  core. The shell, viewer and archive must fit in the remaining ~2.6 MB, or PDFium is loaded on first PDF open
  instead of in the initial load. To be decided with the shell choice.
* The prebuilt WASM is not modularized and defines globals (`out`, `Module`); the product needs its own
  modularized build (`-sMODULARIZE`). Noted for Phase 2.
* WASM is ~1.7x slower than native per page on the same host; still far inside the 1 s first-page budget.

## PoC-4 — LibreOfficeKit on Linux (WP4)

`lok-linux/` · official LibreOffice 26.8.2 x86-64 build, unpacked · LOK headers 26.8.2.2 · first screen =
1080 px wide (Writer / Calc: 1080x1920 window at the top; Impress: whole first slide) · online spell check off
· one process per run, documents opened one after another, 3 runs in different orders.

| Metric | Result |
|---|---|
| Engine install (desktop build, all locales, unstripped) | 734 MB; `program/` 413 MB; `libmergedlo.so` 91 MB |
| `lok_init` (engine load, after profile exists) | ~100 ms, RSS 2 → 99 MB |
| First document, engine not yet loaded: DOCX 20 p. / XLSX / PPTX | 0.58 s / 0.29 s / 0.42 s |
| Engine already loaded: DOCX 20 p. / XLSX / PPTX | 0.23–0.30 s / 0.11 s / 0.10–0.22 s |
| First-screen paint after load | DOCX ~60 ms, XLSX ~36 ms, PPTX ~20 ms |
| RSS with one document open | 210–240 MB |
| RSS after closing every document (3 types opened) | ~300 MB, not returned |

Rendering checked visually: Writer page with header, tables, footer fields; Calc formulas computed (SUMIF,
running totals); Impress bullets and Turkish glyphs.

Findings:

* **Closing documents does not give memory back.** After three documents the process stays at ~300 MB.
  `destroy()` of the whole office instance hangs in this build. "Idle engines are unloaded" (section 3) is
  therefore only achievable by running the office engine in its **own process** that is ended when idle.
  This is an architecture input: the shell talks to the engine over IPC, tiles cross the process boundary
  (shared memory on Linux, `SharedMemory` / ashmem on Android).
* Online spell check must be off for viewing: with it on, Turkish text gets red marks and the first paint of
  the DOCX costs 177 ms instead of 70 ms.
* First run with no user profile: `lok_init` ~190 ms instead of ~100 ms, profile 616 KB. Not a concern.
* The desktop install size says nothing about the Android module budget (≤ 120 MB); that is measured in WP6
  with a stripped, feature-trimmed Android build.

## WP5 (part 2) — Flutter + PDFium on a real phone

Device: **Samsung Galaxy A55 (SM-A556E)**, Exynos 1480, 8 GB (7.3 GB visible), Android 16, 1080x2340 at 120 Hz.
This is an upper mid-range phone, **not the 4 GB reference device** of section 7; memory budgets need a re-check on
a 4 GB phone. Medians of 5 cold starts; one auto-scroll run per renderer through all 101 pages at 300 ms per page.
PSS from `dumpsys meminfo` (what Android's low-memory killer counts), split into graphics and the rest.

| Metric | Impeller (Vulkan, default) | Skia (Impeller off) | Budget |
|---|---|---|---|
| First Flutter frame from process start | 243 ms | 222 ms | ≤ 1.5 s ✓ |
| `am start` TotalTime | 339 ms | 298 ms | |
| Home PSS (graphics + other) | **254 MB** (~155 + ~100) | 96 MB (33 + 63) | ≤ 150 MB: Impeller ✗, Skia ✓ |
| Open 100-page PDF → first page visible | 146 ms (107–181 over 3 runs) | 138 ms | ≤ 1 s ✓ |
| PDFium page render, 1080 px (avg / p90 / max) | 18.7 / 22.1 / 27.3 ms | 18.6 / 20.6 / 24.1 ms | |
| Peak PSS while scrolling the PDF (graphics + other) | **388 MB** (257 + 131) | 294 MB (185 + 109) | ≤ 300 MB: Impeller ✗, Skia ✓ (barely) |
| In-app frame time over 8.3 ms (Flutter `FrameTiming`; see WP8: not what the display shows) | 2.4 % (88 / 3597) | 12.6 % (450 / 3557) | |
| Frame time p50 / p90 / p99 | 3.9 / 5.7 / 10.5 ms | 4.7 / 8.8 / 18.0 ms | |
| Visible page still blank while scrolling | 0.0 % | 0.0 % | |
| Release APK, arm64 | 21.3 MB | same | ≤ 30 MB ✓ |

Findings:

* **Speed is not a problem.** Start, first page and scrolling are far inside the budgets; with Impeller the scroll
  is smooth at 120 Hz and no page is ever shown blank.
* **Memory is the problem, and it is graphics memory.** Impeller on Vulkan holds ~150 MB of GPU memory (`GL mtrack`
  111 MB + `EGL mtrack` 44 MB) before any document is open, so the 150 MB home budget fails before the app does
  anything. The non-graphics part (~100 MB) is within budget.
* Skia meets both memory budgets. Its in-app frame times are longer, but SurfaceFlinger counted 0 missed frames
  for both renderers (WP8 re-run), so the scroll is smooth on screen either way. Flutter logs "Impeller opt-out deprecated": Skia on
  Android is being removed, so it is **not a long-term option**.
* `ImpellerBackend=opengles` in the manifest is ignored on this device: Flutter 3.47 still picks Vulkan (checked in
  the log). An Impeller-on-GLES comparison is not possible here.
* The PDF viewer's own share is tunable: the PoC keeps 12 decoded pages of 6.6 MB each as textures (~80 MB). A
  smaller cache or tile-based rendering lowers the viewing peak; the home-screen baseline does not change.

Consequences for the proposal:

* The section 7 RAM numbers must say what they measure. Options for the owner: (a) keep PSS and raise the home
  budget to ~250 MB for a Flutter shell; (b) budget non-graphics PSS (~100 MB here) and graphics separately.
* The second shell candidate (WP8: Compose / native Android views) must be measured on the same phone, because the
  ~150 MB Impeller baseline is the single biggest number in the light core and the shell decision depends on it.
* A 4 GB reference phone is still needed to confirm the memory numbers.

## WP8 — Jetpack Compose shell, same scenario, same phone

`compose-pdf/` · Jetpack Compose 1.11.4 (BOM 2026.06.01; 1.12 needs compileSdk 37) · Kotlin 2.4.0 · the same
PDFium build through a 50-line JNI bridge, rendering on one background thread into `Bitmap`s shown in a
`LazyColumn` · same page cache (12), same prefetch (about one screen), same auto-scroll (300 ms per page).

Scroll smoothness is now measured for every shell the same way, by SurfaceFlinger (`dumpsys SurfaceFlinger
--timestats`): frames the display actually presented for the app's layer, and how many missed their deadline.
In-app frame metrics (Flutter `FrameTiming`, Android `FrameMetrics`) measure different intervals and are not
comparable; Compose's `FrameMetrics` total even reported 99 % of frames "over budget" on a run where SurfaceFlinger
counted 9 janky frames out of 3 635.

Galaxy A55, one run each on 2026-11-18, cold-start values are medians of 5.

| Metric | Flutter, Impeller (Vulkan) | Flutter, Skia (deprecated) | Jetpack Compose | Budget |
|---|---|---|---|---|
| Release APK, arm64 (shell + PDFium) | 21.3 MB | 21.3 MB | **7.9 MB** | ≤ 30 MB |
| First frame from process start | 207 ms | 227 ms | **139 ms** | ≤ 1.5 s |
| Home PSS (graphics + other) | 256 MB (151 + 105) | 111 MB (38 + 73) | **36 MB** (15 + 21) | ≤ 150 MB |
| First PDF page visible | 132 ms | 99 ms | 84 ms | ≤ 1 s |
| Peak PSS while scrolling (graphics + other) | 392 MB (257 + 135) | 303 MB (175 + 128) | 319 MB (143 + 176) | ≤ 300 MB |
| Display-level janky frames while scrolling | 0 / 3634 | 0 / 3583 | 9 / 3635 (0.25 %) | |
| Visible page blank while scrolling | 0 % | 0 % | 0 % | |
| PDFium render per page, avg | 19.6 ms | 18.8 ms | 17.4 ms | |

Findings:

* **All three scroll smoothly and open the PDF fast.** Speed does not separate the candidates.
* **Memory and size do.** At rest Compose uses 36 MB against Flutter's 256 MB (Impeller). The difference is
  almost all Impeller's fixed GPU allocation (~150 MB); without it (Skia) Flutter is at 111 MB.
* While viewing, the PoC viewers themselves dominate. Compose keeps each cached page twice (a `Bitmap` in native
  memory and its GPU texture: "other" 176 MB); Flutter frees the CPU copy after upload. Both viewers need a
  smaller or tile-based cache in the product; this is viewer design, not a shell property.
* The Exynos 1480 GPU (Xclipse 530) may make Impeller's fixed cost device-specific. The 4 GB reference phone,
  with a different GPU, is needed before this number is used as a decision fact.

Not measured here, but part of the shell decision (section 12): the Linux and Web builds. Compose Multiplatform
runs on the JVM on Linux (a bundled runtime adds tens of MB) and on Kotlin/Wasm with Skia in the browser; Flutter
runs natively on Linux (GTK) and on WebAssembly with Skia in the browser. Both must fit the Web initial-load
budget (≤ 5 MB) together with PDFium (2.4 MB). These are measured next.

## WP6 (part 2) — LibreOfficeKit on the phone, engine in its own process

`lok-android/` · the LibreOffice Android build from WP6 part 1 · Galaxy A55 (see WP5) · a plain-View UI process
binds `EngineService` in a separate process (`:engine`); the engine opens the document, paints the first screen
(1080 px wide, same windows as the Linux PoC) and hands the pixels to the UI through `SharedMemory`. When the UI
unbinds, the engine process ends itself. Bundled fonts: Liberation, Carlito, Caladea (section 6), 8 MB.
Times are "user asks → first screen drawn in the UI", so they include binding, IPC and the pixel copy.

| Metric | Result | Budget |
|---|---|---|
| Typical 20-page DOCX, engine not yet loaded (3 cold runs: DOCX first) | **0.87 s** (engine start 15 ms, init 127 ms, load 375 ms, first screen 281 ms) | ≤ 5 s ✓ |
| Same, very first run after install (assets unpacked first: 49 ms) | 1.14 s | |
| XLSX / PPTX first, engine not yet loaded | 0.47 s / 0.55 s | |
| Typical DOCX, engine already loaded (3 runs) | 0.62 / 0.70 / 0.78 s | ≤ 2 s ✓ |
| XLSX / PPTX, engine already loaded | 0.21–0.34 s / 0.25–0.29 s | |
| Engine process PSS with one document open (4 runs) | 209–228 MB (no GPU memory: the engine renders on the CPU) | viewing; editing ≤ 600 MB not yet measured |
| UI process PSS (plain Views + one 1080 px screen bitmap) | 93–109 MB | |
| After unbind: engine process | **gone in every run**; UI PSS 83–91 MB | |
| Harness APK, arm64 (engine + assets + fonts; libraries stored uncompressed) | 211 MB installed, 81 MB gzip | module ≤ 120 MB ✓ |

Rendering checked on the device screenshots: Writer page with header, table, footer fields and Liberation fonts;
Calc values and formulas; Impress slide with Turkish glyphs. Same output as the Linux PoC.

Findings:

* **The office engine meets every measured time budget on the phone**, with a wide margin, even cold.
* **The separate-process design works on Android**: binding costs ~55 ms, the engine process starts in 15 ms,
  and ending it returns all of its ~220 MB. This is the way to meet "idle engines are unloaded" (section 3).
* Writer sometimes spends 200–280 ms on the first paint right after loading (layout still finishing); a
  progressive first screen (paint what is laid out, refine) would cut the cold DOCX time further.
* Integration notes for the product: the engine's Java bridge expects an `Activity` (changed to `Context`);
  `assets/unpack` must be extracted to the data directory before init (done once, 49 ms); LibreOffice's
  `fonts.conf` points the fontconfig cache at its sample package name and must be rewritten.
* The corpus files are LibreOffice-produced. Microsoft-produced DOCX/XLSX/PPTX and heavier real documents still
  have to be measured (fidelity test plan, deliverable 9).
* Delivery was the "full" variant (engine inside the same APK, the F-Droid / direct-APK row of section 3). Play
  on-demand feature-module delivery was not tested; it needs `bundletool` local testing at least, and is a
  Phase 6 item.

## WP8 (part 2) — shells on Linux and Web

`shell-size/` · the same minimal home screen in both candidates (Material 3 app bar, a button, a 100-row lazy
list) · Flutter 3.47.7; Compose Multiplatform 1.12.1 with Kotlin 2.4.0 (Linux: JVM app image with a jlink'ed
runtime, ProGuard on; Web: Kotlin/Wasm) · `run.sh` builds and measures both. PDF engine not included: add
PDFium's own share (Linux 7.7 MB / 3.2 MB gzip, Web 2.4 MB gzip, from PoC-1/2).

Linux was measured on the development host under WSLg (Wayland on Windows). Start times are comparable between
the two shells; absolute RSS includes WSLg's graphics driver and must be re-measured on a native Linux desktop.
Web sizes are what headless Chromium actually fetched on first load, gzip -9 of those files (brotli would be
~15–20 % smaller for both).

| Metric | Flutter | Compose Multiplatform | Budget |
|---|---|---|---|
| Linux package (shell only) | **22 MB**, 8.5 MB tar.gz | 115 MB (runtime 77 MB), 45.8 MB tar.gz | — |
| Linux first frame from process start (median of 5) | **260 ms** | 1 132 ms (JVM start) | ≤ 1.5 s |
| Linux RSS at rest (WSLg) | ~273 MB | ~225 MB | ≤ 150 MB (Android number) |
| Web first load, shell only, gzip | **2.19 MB** (Wasm/skwasm) · 2.69 MB (JS/CanvasKit) | 4.06 MB (Wasm/Skiko) | |
| Web first load with PDFium | **4.6 MB** · 5.1 MB | 6.5 MB | ≤ 5 MB |
| Off-origin requests on first load | **with default flags: CanvasKit/skwasm and Roboto from Google's CDN**; none with `--no-web-resources-cdn` | none | none allowed (sections 8, 9) |

Both render the screen correctly (screenshots checked: `shell-size/out/`).

Findings:

* **Android and the other platforms pull in opposite directions.** Compose is far lighter on Android (WP8 part 1:
  36 vs 256 MB at rest, 7.9 vs 21.3 MB APK). On Linux and Web Flutter is lighter: 5x smaller Linux package, 4x
  faster start, and the only candidate that fits the Web 5 MB budget together with PDFium (Wasm build, 4.6 MB).
* Compose Multiplatform on Linux carries a JVM: ~1.1 s to first frame and a 77 MB runtime. That is inside the
  1.5 s start budget but leaves little margin, and there is no Linux size budget yet.
* Flutter Web must always be built with `--no-web-resources-cdn` (and bundled fonts); the default build fetches
  its renderer and the Roboto font from Google servers, which the spec forbids.
* Compose Web (4.06 MB) does not fit the 5 MB initial-load budget once PDFium is added, unless PDFium is loaded on
  first PDF open instead of in the initial load.
* Memory at rest on Linux is similar for both (~225–275 MB under WSLg) and above the Android home budget; a
  desktop memory budget does not exist in section 7 and should be added.

## WP7 (part 2) — opening documents in the browser engine

Same build and harness (`lo-wasm/test/`), no rebuild; 2 runs on 2026-11-18, both shown. Documents opened with
`loadComponentFromURL` and `Hidden=true`, then closed; Writer's view `PageCount` is read after loading, which
forces the full layout and is timed separately.

Cause of the part-1 failure: not the frame target (`_default` failed the same way). The engine runs with
`PROXY_TO_PTHREAD`, so the real in-memory file system lives on the browser main thread; `FS.writeFile` called
inside the engine worker only wrote the worker's private copy and the engine saw no file. The page now writes the
corpus into `/tmp` from the main thread (`preRun`) before the engine starts.

| Step (local server, no network time) | Run 1 | Run 2 |
|---|---|---|
| Page start → UNO ready | 12.3 s | 11.9 s |
| New empty Writer document (`private:factory/swriter`) | 223 ms | 281 ms |
| `example.odt` from the engine's own file image | 152 ms | 181 ms |
| Typical 20-page DOCX, first open (20 pages) | **495 ms** + full layout 332 ms | **508 ms** + 346 ms |
| Typical XLSX (2 sheets) | **496 ms** | **511 ms** |
| Typical PPTX (12 slides) | **431 ms** | **887 ms** |
| Typical 20-page DOCX, second open | 182 ms + layout 285 ms | 259 ms + 298 ms |
| Engine start + typical DOCX open + layout | **13.1 s** | **12.8 s** |
| WASM heap | 1 024 MB (fixed) | 1 024 MB |

* **Once the engine is up, documents open in about half a second** (DOCX 0.5 s + 0.3 s layout, XLSX 0.5 s,
  PPTX 0.4–0.9 s): close to the Linux native times of WP4 (0.3–0.6 s cold) and inside the 5 s / 2 s DOCX
  budgets.
* **The cost is the start**: ~12 s of engine start (on a 16-core desktop, files served locally) dominates the
  first document; with the 76.8 MB download on a 50 Mbit/s line add ~12 s more. A cached second visit still pays
  the ~12 s start.
* Memory: the heap is a fixed 1 GB block reserved at start. `measureUserAgentSpecificMemory` reports 2.2 GB
  before and 4.25 GB after the documents; it most likely counts the shared heap once per engine thread, so it is
  not used as a figure.
* Measured in part 3: the trimmed engine. Not measured yet: a mid-range laptop, rendering a page to the screen
  (only load + layout here).

## WP7 (part 3) — trimmed engine: file-system image only

`lo-wasm/trim.sh`, same `soffice.wasm` / `soffice.js` (no rebuild): only the file-system image `soffice.data` is
repackaged with Emscripten's `file_packager`. Removed: the dialog definitions (`soffice.cfg/**/*.ui`) except the
three the engine opens headless, gallery, wizards, splash images, and every font except the product set
(Liberation, Carlito, Caladea) and OpenSymbol. 1 168 of 1 888 files, 72.5 MB raw.

Which `.ui` files are needed was traced with an `FS.open` hook while loading the three documents: only
`svt/ui/scrollbars.ui`, `svt/ui/tabbuttons.ui` and `modules/simpress/ui/tabviewbar.ui`. Removing all `.ui` files
makes every `loadComponentFromURL` return null.

Bisecting (one run each): removing only the fonts takes the engine start from ~11 s to **2.0 s**; removing only
the dialog definitions or the extras does not change the start (10.6–10.8 s). **The slow start was the font scan
of the 129 bundled fonts (51 MB)**, not the engine code. The product set also lays out the typical DOCX to the
same 20 pages.

Memory is now Chromium's whole process tree, PSS after the test (`measure.mjs`), instead of the browser API.

| Metric (local server, no network time) | Untrimmed | Trimmed, run 1 | Trimmed, run 2 |
|---|---|---|---|
| `soffice.data` | 92.9 MB raw / 27.0 MB gzip | 20.4 MB raw / **6.8 MB gzip** | |
| Total engine download | 76.8 MB gzip | **56.7 MB gzip** (of which `soffice.wasm` 49.7 MB) | |
| Page start → UNO ready | 11.3–12.3 s | **2.1 s** | **2.1 s** |
| Typical 20-page DOCX, first open + full layout | 0.5 + 0.3 s | 0.36 + 0.23 s | 0.41 + 0.27 s |
| Typical XLSX / PPTX | 0.5 / 0.4–0.9 s | 0.40 / 0.33 s | 0.42 / 0.42 s |
| Typical DOCX, second open + layout | 0.18–0.26 + 0.3 s | 0.16 + 0.14 s | 0.16 + 0.19 s |
| Engine start + typical DOCX open + layout | 12.8–13.1 s | **2.7 s** | **2.8 s** |
| Chromium PSS, whole process tree | 998 MB | **902 MB** (largest process 535 MB) | |

Mid-range machine indication (one run each, Chromium pinned with `taskset`, same fast cores):

| Cores | UNO ready | DOCX open + layout | XLSX | PPTX | Start + DOCX | PSS |
|---|---|---|---|---|---|---|
| 4 | 2.2 s | 0.30 + 0.22 s | 0.45 s | 0.51 s | 2.7 s | 888 MB |
| 2 | 2.6 s | 0.57 + 0.45 s | 0.74 s | 0.73 s | 3.6 s | 896 MB |

* **The trimmed engine meets R3 on this machine**: 56.7 MB gzip (≤ 60), typical DOCX laid out ~2.8 s after page
  start (≤ 10 s), ~0.9 GB for the whole browser (< 1.5 GB). Even on two cores it stays at 3.6 s.
* Download, not start, is now the first-visit cost: 56.7 MB is ~9 s at 50 Mbit/s, once; the browser then caches
  it. `soffice.wasm` is 88 % of it, so the next lever is the code itself (Writer-only module), not the data.
* Still open: a real mid-range laptop (slower cores than the pinned runs), the Writer-only module, a smaller
  initial heap (the 1 GB is reserved but only touched pages count), and the fonts needed for non-Latin scripts
  (only Latin product fonts here; the font set must be decided with the fidelity corpus).
